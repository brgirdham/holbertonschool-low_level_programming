Measurement Methodology:
The purpose of this topic was to calculate the time it took the CPU to run a certain program and why sometimes the same amount of data can take different amounts of time every time it gets run. This is shown by me using the first .c file - baseline_loop.c - to run through the computaton of the file and produce an elapsed time of how long it took to run the file. This task asked me to run the file multiple times to understand that een though it was the same file, it will finish at different points in time. From my results of running the file the first instance took 0.205176 seconds, then 0.204560 seconds and finally 0.204939 seconds. As we can see from the data it shows that even the simplest files can still have different end times even it is by less than a fraction of a second.

Observed Performance Differences:
This task showed how there can be multiple ways in sorting/running a file. Using the file it compared time from running the file one way versus the other, as both times were elapsed it showed a clear difference in which way is better suited to run the file as quickly as possible. In my 5 tests of the file, the average of the 'Naive' way was 2.4869954 seconds, whilst the "Single-Pass' way did it in 0.000097 seconds. THAT IS OVER 25,000 TIMES FASTER. 

Relation Between Runtime and Energy Consumption:
The relation between both runtime and energy consumption is a complicated one, there a definitely advantages of having a faster runtime, but it all relate back to the simplicity of a file. This is one key way to decrease the energy consumption whilst executing a file, you need to have more efficient data structures and remove unused code so that it doesn't take more electricity to simply run something that doesn't even get used. Knowing how to cut down on these smaller concepts helps better the use of all areas of the computer system.

Limitations of the Experiment:
I would say the few limitations of this experiment is that I am only running a few simple lines of code that are already optimised to run the quickest time it possibly can. As well as it being a smaller file I can't know how long a longer more complex file would take and what the computational cost would be to run them. The last limitation would be that I wasn't building a code from scratch so I wouldn't know the difference between when I first write my code to when it has been optimised to maximum efficiency and what the difference of time it would be to run the first version to the final version.

Practical Engineering Takeway:
The takeaways I have gotten from this project is that although code can work using multiple different ways to catch certain inputs, it can be better to reduce the complexity of the code to it's basic functions and still being able to work. I found this out when writing the clock_t variables, instead of havng end1, end2 and so on, I was able to reduce it to just two sets of variables instead of having the file constantly check between 4 variables for each line of code that it was running. Understanding this also helped me to clean up the code, instead of it being messy and long it was clean and concise which can also help notice this pattern in other parts of the code as well.
